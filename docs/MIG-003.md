## 4. StatefulShellRoute frente a ShellRoute

`StatefulShellRoute.indexedStack` mantiene un Navigator por rama y conserva su
pila en memoria. Un ShellRoute simple compartiria una sola pila y exigiria
gestion adicional para recordar cada seccion. No existe NavigationNotifier ni
una copia de la seleccion en Riverpod. Las ramas se cargan al visitarlas.

Scopes de restauracion: `fudi-app`, `fudi-router`, `consumer-shell`,
`consumer-shell-page` y un scope estable por rama. Cada Page usa una identidad
restaurable. Esto prepara seleccion y rutas; no es persistencia de datos de negocio.

## 10. Integracion go_router

ConsumerShellPage adapta AppDestination a las primitivas. selectedIndex procede
exclusivamente de `navigationShell.currentIndex`. `goBranch` conserva otra rama;
reseleccionar la activa usa `initialLocation: true` para volver a su raiz.
El router desactiva la solicitud automatica de foco al navegar para no robarlo
al control activado; el shell consumer establece su foco inicial explicitamente.
En web FudiApp mantiene un SemanticsHandle durante su vida, sin exigir activar
el control oculto Enable accessibility del motor. En native se conserva el
comportamiento de accesibilidad de plataforma; el handle web se libera al desmontar.
La pequena Page privada solo configura recorrido de foco y delega la ruta
al framework; no intercepta back ni gestiona historiales manualmente.

## 11. Back

Android back delega al router: desapila la rama activa, sin afectar las demas.
En su raiz no fuerza Inicio: devuelve el control al SO. Cambiar tabs no crea
una pila artificial de pantallas consumer en el Navigator raiz.
Web back/forward recorre el historial de URLs, tambien los cambios de tabs.
Una ruta hermana abierta con push puede volver a su rama de origen con pop.
Reseleccionar un tab restablece solo su raiz.

Las pruebas duplican un placeholder mediante push con query para verificar
pilas sin registrar features de mentira. No se promete que un push imperativo
sea una URL publica persistente; los detalles futuros usaran rutas declarativas.

## 12. Deep links

La ubicacion inicial de produccion se deja a go_router y la plataforma, no se
fuerza `/` sobre un enlace entrante. Hoy se pueden abrir y recargar los cuatro
placeholders directamente. Se conserva la estrategia hash web de MIG-000:
`/#/discover`, `/#/bookings`, `/#/account`; no hay indices de tabs en las URLs.

IDs/slugs/codigos seran parametros semanticos para restaurante, recomendacion,
reserva publica y perfil. Compartir un recurso no dependera de extra ni del tab
previamente seleccionado. Resolver enlaces web existentes hacia app o web
publica se decidira en hosting/deep links, con aliases explicitos y auditados.
No se configura Universal Links, App Links, manifest de asociacion ni path URL
strategy. Codigo de reserva y token no deben registrarse en logs ni analytics.

## 25. Riesgos

- Falta validacion en dispositivos reales, gestos iOS/predictive back Android,
  teclado virtual y lectores de pantalla nativos. Widget/web no equivalen a hardware.
- La restauracion recupera seleccion y una rama visitada con pila imperativa.
  Se observo perdida de una pila imperativa cuando pertenecia a la rama de
  arranque y despues quedaba inactiva al reiniciar. No hay workaround del SDK
  ni persistencia manual: revisar en su fase con detalles declarativos reales.
- Restauracion no significa conservar todas las pilas tras un reload web:
  un reload reconstruye el recurso de la URL actual, no historial de producto.
- Cuatro labels conocidos se comprueban completos al 200%; etiquetas futuras
  mas largas requieren nueva revision. Tooltip/semantics conserva el label completo.
- Auth, permisos locales/SSR, aliases contradictorios y sitemap legacy requieren
  reconciliacion, no traslado automatico. Los ajustes OpenAPI y LocalDateTime
  siguen siendo riesgos de MIG-001, sin cambios en esta fase.
- El motor web mantiene su CDN CanvasKit. Las fuentes y logo estan locales.
  No se resuelve publicacion offline, SEO ni asociaciones de enlaces nativos.
